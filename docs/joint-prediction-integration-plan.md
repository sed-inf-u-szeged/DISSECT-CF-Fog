### Source facts affecting the design

- CityTopology reuses configured city coordinates rounded to one decimal
  degree (for example Budapest 47.5/19.1 and Szeged 46.2/20.1). These are
  approximate geographic placements, not surveyed server locations, road maps
  or recorded real-device movements. Fog access circles are experimental.
- All configured devices are created before one shared simulation advances.
  Their events share nodes and simulation time. One Python worker handles
  isolated device model sessions sequentially; this is not 100 separate
  full simulations or 100 simultaneous model workers. The 1-100 limit is
  explicitly enforced in UI/Python/Java and is not a measured physical maximum.
- The original prediction chart aligns each model's first future target at
  relative zero. Shared absolute simulation time must also be checked before
  calling model forecasts directly comparable.
- Current learned load forecasts contain 64 targets and are issued at eligible
  origins at least 64 samples apart per version. A replay frame does not imply
  that every model issued a new vector then. Short 120-minute runs cannot
  supply the 287 raw points needed for the first load-model fit.

## First runtime contract (proposal)

1. One run identifier, scenario configuration and simulation clock. Separate exogenous workload/movement seeds from controller randomness, or replay the same external event trace for controller comparisons.
2. Sample every configured 60,000 simulation milliseconds, once per node per timestamp. Specify ordering after state-changing events at that timestamp. Record `sample_phase` explicitly. The sampler must terminate independently of task draining.
3. Record `run_id`, `node_id`, `time_ms`, `sample_index`, `sample_phase`, `waiting_assignment_bytes`, `running_tasks`, `completed_tasks_total`, `connected_devices`, upload and offload counters. Derive interval flows from cumulative counters only within the same run. Do not count offloads as newly generated data.
4. Each prediction identifies task, entity, model/version, last input time, origin time, target time, horizon and units. A 64-step load forecast has 64 distinct target timestamps. The mobility forecast remains a 60-second target. Do not equate different horizons or force identical input-window lengths.
5. Emit actuals independently. Score a prediction only after its actual target is observed. Keep retrospective UI target markers out of training/serving inputs. Do not interpolate from future samples or fill the final draining gap with invented labels.
6. Start load integration with a persistence baseline on the shared series. Then connect the existing trained load models behind an explicit adapter/profile. Allow a configurable long movement run (initial smoke proposal: 6-8 simulated hours); determine actual required duration from training and qualification events, not a nominal end time.
7. Record training/inference wall time separately from simulation time. Missing timing remains unavailable, never zero.
8. Keep energy counters cumulative with declared units and scope. Validate conversion using a constant-power case. Stop samplers/meters explicitly so they do not prevent simulation completion. Record cloud/transfer/wake-up costs where modeled and declare omissions.

## Controller research proposal

Hypothesis: future device arrivals/departures add useful information to load history, allowing earlier capacity activation and longer safe idle intervals than a controller using only current state.

Candidate actions: retain current capacity; activate a configured spare host/VM; place new work elsewhere; migrate supported work; drain and suspend an idle host. Capacity remains bounded by configured hardware. A stationary device can still generate work, and a node without local devices can still process offloaded work.

Start with a transparent threshold controller with separate scale-up/scale-down triggers and a minimum hold time. Add forecasted demand, an uncertainty margin, wake-up delay and transfer cost as separately testable changes. Select thresholds on development scenarios; evaluate on held-out scenarios and seeds. A rolling-horizon optimizer is a later candidate, not a promised improvement or global optimum.

Compare fixed capacity, reactive control, load-only predictive control, and mobility-plus-load predictive control under the same external jobs and movement. Measure total modeled energy, task latency, completed/unfinished/rejected work, overload and switching/offload counts. Report trade-offs until service-quality limits are agreed. Do not achieve apparent energy savings by generating fewer jobs or omitting cloud consumption from the stated boundary.

Dynamic coverage/access control follows a separate definition of bandwidth, admission, reachability, power and wake-up behavior. Changing a map radius alone does not establish an energy model.
