Mobility workflow：模拟器内影子推理

本周收尾目标中的第一步：模拟器正在运行时，把已经发生的观测发送给固定模型，接收 60 秒后的预测。本步骤只验证推理接入，不计算新的位置误差，不改变节点连接策略，不启动 UI，也不重新训练。

数据怎样流动

  1. Java SmartDevice 完成当前时刻的移动与连接更新。
  2. MobilitySampleRecorder 写出实际观测，并返回同一条 CSV 数据。经纬度、观测速度、方向角和有效性标记与训练数据来源一致。
  3. Java 将本条记录送入常驻 Python 进程。Python 仅保留最近 8 个历史点，没有读取路径配置或未来目标的接口。
  4. 按训练时的固定投影、特征顺序和已保存 scaler 构建输入。预测下一分钟的位移并转为经纬度。保持位置、恒速预测在相同起点同时记录。
  5. Java 收到预测，检查起点时间、目标时间和坐标有效性，记录模拟时钟，再继续运行后续事件。

等待 Python 使用真实运行时间，不推进模拟时钟；因此这是同步接入，不能把它解释为已模拟真实网络或推理延迟。模型只加载一次。训练状态保持冻结。

为什么是 121 条观测、112 个预测起点

第一条观测没有可计算的速度和方向，因此首次有效输入需要先收到 9 条原始观测，再使用其中最后 8 条。首个预测起点是索引 8，最后一个是索引 119；索引 120 只接收观测，不再向窗口范围之外预测。共 112 个起点，三种方法合计 336 条预测记录。未连接节点的观测也保留。

运行

安装后，在项目根目录、dissect-fog 环境执行：

python predictor-ui/scripts/mobility/test_mobility_shadow.py
python predictor-ui/scripts/mobility/run_mobility_shadow.py --training "原始完整训练结果目录"

默认使用已有开发场景 triangle.properties。它用于接入正确性检查，不构成新的独立模型性能测试。脚本复制模型、Java 运行依赖和源码到独立结果目录，再编译六个场景相关 Java 文件。不会修改 target/classes；仍需已存在的 target/classes、依赖 JAR、JDK 和当前 Python 环境。

不要单独用 Java Run 来验证此步骤：普通 Run 保留现有行为；本入口向 Java 子进程设置专用环境变量，启用影子推理。支持 --java 指定 JDK java 可执行文件，支持 --project-root 指定项目目录。

observations=121 prediction_origins=112 methods=3
feature_parity=EXACT reply_timing=SAME_SIMULATION_TICK accounting=PASSED
training=DISABLED evaluation=NOT_IMPLEMENTED_THIS_STEP connection_control=DISABLED
MOBILITY_SHADOW_STEP1_OK
