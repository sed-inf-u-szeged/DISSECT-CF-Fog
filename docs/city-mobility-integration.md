# W06.1a: shared city infrastructure for mobility and node-load prediction

Date: 2026-11-16. A short Windows city run is confirmed by user screenshots.
W06.1a2 improves readability; its Windows visual acceptance is pending.

## What changes

`CityTopology` now supplies the original workload infrastructure to both
`PredictionSimulationDefinition` and the optional city profile of
`MobilityPredictionSimulation`. A new city run uses nine fog nodes and
`Budapest_cloud`, with their original coordinates, hardware XML definitions,
VM types/prices, parent links, peer links and network latencies.

The old workload entry point retains its static devices, LoadBalanced device
strategy, 10,000 km range, energy collectors and prediction settings. The
two-node Mobility profile and old saved results remain supported.

| Role | Nodes | Parent |
| --- | --- | --- |
| Cloud | Budapest_cloud | None |
| Regional fog | Gyor_fog1, Kecskemet_fog1, Gyongyos_fog1 | Budapest_cloud |
| Local fog | Sopron_fog2, Szombathely_fog2 | Gyor_fog1 |
| Local fog | Szeged_fog2, Pecs_fog2 | Kecskemet_fog1 |
| Local fog | Miskolc_fog2, Debrecen_fog2 | Gyongyos_fog1 |

These are simulated resources with city labels and configured coordinates.
The input is generated by the simulator; it is not measured traffic from these
cities, and this update does not import an old experiment's forecasts.

## City scenario rules

- UI infrastructure: `Hungary cities · 9 fog + 1 cloud` (new UI default).
- New UI default: nine devices, distributed across the nine fog cities, with
  120 movement minutes. The CLI retains the two-node default if the
  infrastructure field is absent, so existing configurations remain valid.
- Distribution is deterministic round-robin, in the table/source order. Nine
  devices place one at each fog city. Alternatively, choose one starting city
  for all devices. Budapest cloud is not a device starting/access node.
- Fog access radius defaults to 20 km; the supported experimental input is
  1–100 km. It is a synthetic geometric connection rule, not a measured radio
  coverage area. Cloud has no direct device access circle.
- RandomWalk is centred at each device's starting city. Nomadic waypoints are
  offsets in metres translated to that device's city. The default route is a
  local route, not intercity travel. Root legacy start coordinates describe
  the route template; actual per-device starts are recorded in the device
  manifest and `device_start_*` properties.
- Movement uses the existing official strategies, speed parameters and shared
  seeded random stream. Devices attach using StableConnectionDeviceStrategy.
  An out-of-coverage device may be disconnected; a city label does not force
  attachment to that city.
- Each device retains the Mobility generator's 100 bytes per minute. City
  applications use the original workload task size of 5,120 B and 480
  instructions per full task, and the existing Pliant reactive strategy.
  The small two-node profile retains its original task/strategy settings.
  The two profiles therefore are not a controlled capacity comparison.
- Offloading follows available parent/peer links. Cloud can receive offloaded
  work although devices cannot attach to it. Light demand may leave cloud
  and other nodes idle; zero measured backlog is valid in that case.

## Shared data and forecasts

All nodes, including idle nodes and the cloud, have identities in the new
`node_topology.json`. The file stores the run identity, roles, coordinates,
access radii, host/VM CPU and memory, application parameters and links. Frozen
batch sources also include the two fog XML resource files. Device start
coordinates and optional starting-city IDs are in `multi-device.json`.

Mobility input validation now uses the current run's serviceable node list.
It still rejects unknown nodes and device connections to cloud. Each device
retains its own history, learned versions and lifecycle. Additional
IMM/Kalman, XGBoost and TCN mobility models remain shadow comparisons.

Node-load sampling covers all ten nodes on the existing 60-second grid. The
target is bytes waiting for assignment to compute (`receivedData -
processedData`), not CPU utilisation or completed work. Persistence, LSTM and
TCN use these observations from the same run. The worker selects one explicit
node column for training, including cloud when requested; the standalone
trainer's default fog-only column selection is unchanged.

Load input/output remain 192/64 points. The first fit needs 287 raw points
(32 windows); a 120-minute run cannot train a load model. A 480-minute run is
the next full lifecycle check. The candidate profile still requires 64 matched
targets and at least 80% within max(0.1 B, 20% of actual magnitude), with
SMAPE <= 200%; MAE/RMSE have no pass limit in this experimental profile.
The permissive Observe profile is for workflow checks. Constant-zero idle
nodes passing qualification do not establish useful general prediction.

## UI acceptance

1. Restart with `MobilityPredictorUi.java` after installing the update.
2. Start a **new** city run: RandomWalk, nine devices, distributed cities,
   120 minutes, 20 km access radius. For the first quick check, turn off the
   three optional mobility comparisons and both trained load models.
3. When complete, the map should contain nine fog nodes plus the cloud marker.
   The compact city overview shows geographic context; `Device detail` magnifies
   local movement. Select a city button or `Node coverage` to see its true radius.
   Device 0 starts at Sopron; Device 3 at Szeged; Device 8 at Gyongyos.
4. Click `Node load`. The node selector must list all ten nodes. In this short
   run, select Persistence; no trained load versions are expected.
5. Open the prior two-node result and confirm that its labels/results remain
   unchanged. It cannot become a city run merely by opening it in the new UI.
6. After the short-run acceptance, run 480 minutes with LSTM and TCN load
   models if trained city-load curves are needed. This is more expensive than
   the old two-node case because each model is trained separately per node.

The current load panel still displays one chosen model vector with actuals
and paired Persistence. Simultaneous model curves are W06.1b, and live load
chart updates are W06.1c. Existing live mobility preview is distinct from live
node-load prediction charts. In a completed run, seeking backward hides
future observations, future training versions and future evaluations.

## Research boundary and next work

City forecasts do not control capacity, connection choices or offloading.
This step supplies a common multi-node simulation for the planned research.
W07 validates scenarios/seeds/scale; W07.1 tests mobility-informed demand;
W08 defines compute/access actions, energy accounting and service constraints;
W09 compares fixed, reactive and predictive controllers. No energy saving,
100-device city scalability, or improved forecasting accuracy is claimed here.

See `joint-prediction-progress.md` for automated checks and pending acceptance.
